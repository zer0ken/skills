# tdd-is-dead

TDD를 하지 않는다. 테스트는 작성하되, 코드의 맥락을 이해하지 않은 채 테스트를 대충 작성하고 실행과 수정을 반복하는 방식은 시간 낭비이므로 금지한다. 테스트 실행은 이해를 대신하지 않고, 이해한 내용을 확인하는 수단이다.

## 순서

1. **작업 범위 파악.** 바꿀 코드, 호출자, 구현체, 영향을 받는 테스트와 설정을 읽고 수정 범위를 정한다.
2. **작업 의도 파악.** 이슈, 요구, 기존 코드와 커밋이 해결하려는 문제를 이해한다. 의도가 불분명하면 구현 전에 사용자에게 확인한다.
3. **목표 테스트 작성.** 작업 목표가 달성되었는지 판정하는 테스트를 작성한다. 구현 세부가 아니라 합의한 동작을 검증한다.
4. **기존 의도를 존중하며 구현.** 기존 구조, 명명, 관례와 설계 판단을 유지한다. 범위 밖의 코드는 고치지 않는다.
5. **스스로 재검토.** 실행 전에 diff를 다시 읽고 경계 조건, 오류 경로, 누락된 호출자, 타입과 계약 위반을 점검한다.
6. **최소 테스트 실행.** 수정 범위를 커버한다고 판단되는 최소한의 테스트만 실행한다. 실행한 테스트와 그 범위를 선택한 근거를 기록한다.
7. **실패 시 앞 단계로 복귀.** 6단계가 통과하지 않으면 실패 원인이 범위 이해, 의도 이해, 테스트, 구현 중 어디에 있는지 판단하고 해당 단계부터 다시 수행한다. 원인을 이해하지 않은 채 코드나 테스트를 고쳐 다시 실행하지 않는다. 테스트를 통과시키려고 기대값을 바꾸거나 테스트를 건너뛰지 않는다.
8. **전체 검증.** 전체 테스트 또는 PR CI로 전체를 검증한다. 실행 시간이 길면 사용자에게 명령을 전달한다. 설계 판단이나 위험이 남아 있으면 사용자에게 리뷰를 요청한다.

## 보고

결과를 보고할 때 실제로 실행한 테스트, 커밋, 범위를 밝힌다. 실행하지 않은 검증과 실패한 검증을 통과로 계산하지 않는다.
