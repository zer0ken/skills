# rv

결함이 존재한다고 전제하고, 검토 범위의 모든 결함을 찾는 것을 목표로 한다. 동작과 완료 주장을 반박할 입력·실행 순서를 찾고, 결함을 발견하면 같은 원인이 전파되는 경로까지 추적한다. 지적은 발생 조건과 도달 가능한 코드 경로로 입증한다.

절은 비용이 적은 검토부터 차례로 둔다. 앞 단계는 도구 출력(`git diff --stat`, `git ls-files`, 검색, import 계약, LSP 참조)으로 범위를 좁히고, 파일 본문은 뒤 단계에서 좁힌 경로만 읽는다. 앞 단계에서 찾은 결함과 판정은 뒤 단계의 읽을 범위를 정하는 데 다시 쓴다.

## 준비

대상 head, 비교 기준과 미커밋 변경을 확인한다. 프로젝트의 모든 규칙과 참조 규칙을 정독하고 적용 경로를 대조한다. 프로젝트 리뷰 규칙, `osiri`의 해당 가이드와 `refactor`를 함께 참조한다.

기존 리뷰·응답·사용자 결정·검증 결과를 현재 코드에 대조한다. 이전 지적은 각각 재확인하고, 판정이 달라지면 이유를 남긴다. 재확인은 지적의 위치만 읽어 먼저 끝낸다.

## 코드베이스 검토

파일 본문을 읽기 전에 구조 정보만으로 끝내는 단계다. 목록, 이름, import 관계, 규모는 도구 출력으로 확인하고, 의심스러운 파일만 열어 본다.

코드 내용과 별개로, 변경이 남기는 코드베이스 자체의 모양을 검토한다. 범위는 diff 줄이 아니라 변경이 닿은 패키지와 그 이웃이며, 변경 전부터 있던 문제라도 변경이 그것에 기대거나 키우면 지적한다. 아래 유형은 동작과 검사 통과 여부와 무관하게 결함으로 지적하고, 지적에는 원인인 책임 배치와 옮길 위치·바꿀 이름을 함께 적는다.

1. import 관계와 `__init__.py`
  1.1 계층 역전: 아래 계층이 위 계층을 import 한다(프로젝트의 계층 규칙과 import 계약 기준).
  1.2 공개 경로 우회: 패키지가 공개한 경로 대신 내부 모듈을 직접 import 한다.
  1.3 `__init__.py` 이상: 내부 구현의 이유 없는 re-export, 같은 심볼의 여러 import 경로, 쓰지 않는 공개 이름, import 시점의 무거운 로딩·부작용, 하위 모듈과 대칭이 아닌 이름.
  1.4 private 이름 접근: 다른 모듈의 `_name` 을 import 하거나 시험이 내부를 단언한다.
  1.5 순환 회피 흔적: 함수 안 import, `TYPE_CHECKING` 은닉, 지연 import 로 순환을 피한다.
  1.6 검사 우회: import 계약의 ignore 줄이나 `noqa` 로 경계 위반을 덮는다.
  1.7 소유자 중복: 한 개념을 여러 패키지가 정의하고 서로 import 한다.
2. 디렉터리 구조
  2.1 배치: 한 개념이 여러 디렉터리에 흩어지거나, 한 디렉터리가 서로 무관한 개념을 섞는다. 외부 인터페이스는 리소스 단위, 내부 core 는 기능 단위라는 프로젝트 배치 규칙을 어긴다. 최상위 디렉터리가 기능이 아니라 구현 계층이나 조회 유형을 드러낸다.
  2.2 쪼개기와 껍데기: 내용이 거의 없는 파일·디렉터리, 다른 모듈을 그대로 넘기기만 하는 모듈, 한 곳에서만 쓰는 작은 파일 분할.
  2.3 시험·fake·fixture 배치가 제품 코드의 배치와 대응하지 않는다.
3. 파일·모듈·식별자 이름
  3.1 이름과 내용의 불일치: 이름이 담은 책임을 가리키지 않거나, 같은 개념이 곳마다 다른 이름이거나, 짝을 이루는 모듈(예: 프롬프트 모듈과 그 사용 모듈)의 이름이 대칭이 아니다.
  3.2 이름 품질: 도메인과 코드에 없는 말, 뭉뚱그린 이름(`utils`, `helpers`, `common`, `misc` 류), 대상과 맞지 않는 단·복수, 프로젝트 이름 규칙(검사기, AGENTS.md, main 의 기존 배치) 위반.
  3.3 이동·이름 변경의 잔재: 옛 이름이 문서, 시험, patch 대상, 직렬화 키, 설정에 남아 있다.
4. 규모와 잔재
  4.1 변경 전후의 파일·줄·모듈·클래스·함수 수를 비교하고, 문제 해결에 비해 커진 부분을 지적한다.
  4.2 호출자 없는 코드, 쓰이지 않는 설정 키·질의·schema 객체, 폐기한 기능의 시험·문서가 남아 있다.
  4.3 디렉터리 AGENTS.md, README, 설계 문서가 실제 배치·이름·계약과 다르다.

## 구조와 품질 판단

변경의 진입점, 공개 인터페이스, 데이터 모델과 설계 문서만 읽고 판단한다. 구조가 대안보다 못하다는 판정이 나오면 그 판정을 먼저 기록하고, 다음 단계의 세부 검토는 바뀌지 않을 부분에 집중한다.

리뷰는 결함 탐색과 별도로 다음 두 질문에 근거와 함께 답한다. 이 판단은 생략하지 않으며 결과 문서에 별도 절로 남긴다.

1. 이 구조가 문제를 논리적으로 실제 해결하는 가장 적합한 구조인가.
  1.1 해결하려는 문제를 원인 수준으로 다시 서술하고, 변경이 그 원인을 제거하는지, 증상만 우회하는지 판정한다.
  1.2 데이터 흐름, 상태 소유, 책임 배치, 단계 분할, 호출 비용(DB 왕복, 모델 호출)을 기준으로 실현 가능한 대안 구조를 최소 하나 세우고, 현재 구조와 비교해 어느 쪽이 정확성, 성능, 단순성에서 나은지 판정한다.
  1.3 현재 구조가 대안보다 못하면 구조 결함으로 지적한다. 동작이 맞아도 지적한다.
2. 그 구조 안에서 낼 수 있는 최고의 품질에 도달했는가.
  2.1 구현, 프롬프트, 질의, 시험, 문서가 그 구조가 허용하는 상한에 비해 어디서 손실을 내는지 찾는다.
  2.2 측정이 있으면 기준(main 등) 대비 모든 지표를 대조하고, 나빠진 지표는 원인과 함께 지적한다. 측정이 없으면 측정 공백으로 기록한다.
  2.3 남은 차이가 구조의 한계인지 구현의 미흡인지 구분한다. 구조의 한계는 1번 판정으로, 구현의 미흡은 결함으로 기록한다.

사용자가 명시적으로 후속 범위로 합의한 품질 차이는 결함이 아니라 후속 범위로 분류하되, 위 두 판정 자체는 수행해 기록한다.

## 세부 검토

앞 단계가 좁힌 경로를 따라 본문을 읽는 가장 비싼 단계다.

관련 파일 전체와 호출자·백엔드·fake를 읽고 입력→상태 소유→쓰기→실패→복구를 추적한다. 부분 완료, 복구 중 실패, 재시도, 동시 실행·취소에서 계약과 자원 정리가 유지되는지 공격적으로 검증한다. 방어 로직과 시험이 놓치는 반례를 찾는다.

수정이 원인을 직접 해결하고 구조를 단순하게 만드는지 확인한다. 동작하더라도 불필요한 분기·중복·wrapper·추상화와 폐기되지 않은 옛 경로는 구체적인 영향과 단순화 방향을 지적한다.

품질·성능·완료 주장을 실제 결과와 대조한다. 검증은 SHA·입력·환경·범위와 최신 실행 결과를 확인한다. CI 통과를 다른 경로의 정확성이나 품질 보장으로 확대하지 않는다. 결함, 검증 공백과 명시적으로 합의된 후속 범위를 구분한다.

핵심 경로, 기존 미해결 지적과 필수 검증을 끝까지 대조한다. 확인하지 못한 범위는 남기며 결함을 모두 찾았다고 단정하지 않는다. 수정·외부 게시·DB·모델·벤치마크 실행은 사용자 승인 범위를 따른다.

## 결과

프로젝트의 형식·심각도·상태 체계를 우선하고, 별도 형식이 없으면 아래 형식을 쓴다. 참고 형식은 graphai-repository/enterprise-memory PR #1208 리뷰 `pullrequestreview-5646450494`다. 한 줄에는 판단 하나만 적고, 판단을 뒷받침하는 재현 절차, 스크립트, 실행 출력과 집계 목록은 본문에 넣지 않고 별도 자료로 둔다.

1. 판정: 첫 문단 두세 문장에 판정, 대상 head와 merge-base, finding 수와 심각도별 건수, 상태와 근거 구분의 뜻을 적는다.
2. 인덱스: 지적이 두 영역 이상에 걸치거나 후속 리뷰이면 섹션·범위·심각도·상태·최신 코멘트·다음 행위자 표를 둔다.
3. 판정 근거: 코드베이스 검토 네 항목과 구조·품질 판단의 두 질문에 대한 답을 한 절에 서너 문장으로 적는다. 비교한 대안 구조는 한 문장으로 적고, 결함은 지적 목록에 기록한다.
4. 지적: 검토 영역별 `###` 절 아래 finding 하나를 `-` 항목 하나로 쓴다.
  4.1 형식은 `R-001 심각도, 근거 구분: 문제. 위치. 조치.`이며 근거 구분은 재현·관찰·추론이다.
  4.2 문제는 발생 조건과 결과를 한 문장에 적고, 수치는 괄호 안에 짧게 적는다.
  4.3 위치는 대상 head 의 `파일:줄`만 적고, 조치는 한 문장으로 적는다.
  4.4 항목이 세 문장을 넘으면 finding을 나누거나 근거를 줄인다.
5. 검증 범위: 마지막 `###` 절에 실행한 검증과 통과·실패 수, 실행하지 않은 검증을 한두 문장으로 적는다.

기본 심각도는 BLOCKER·MAJOR·MINOR·NIT다. 미해결 BLOCKER·MAJOR와 구조가 대안보다 못하다는 판정은 변경 요청, 핵심 검증 공백으로 판단할 수 없으면 판단 보류다.

후속 리뷰는 기존 ID와 의견을 보존하고 응답은 `A-001`, 재확인은 `R-001-C`로 기록한다. 상태는 OPEN·ANSWERED·RECHECK·RESOLVED·SKIP이며 수정과 증거를 확인해야 RESOLVED로 바꾼다. SKIP에는 이유를 적는다.

## 작성과 게시

결과 문서는 터미널 출력과 외부 게시 모두 작성 전에 `sucks` 스킬을 로드해 적용한다. 종결어미는 프로젝트 규칙이나 참고 형식을 따른다.

PR 리뷰나 코멘트로 게시하는 절차는 다음과 같다. 게시와 수정은 사용자 승인 범위에서만 수행한다.

1. 게시 전에 PR 의 기존 리뷰와 코멘트를 다시 읽는다. 같은 head 에 다른 판정의 리뷰가 있으면 게시하지 않고 사용자에게 보고한다.
2. 저장소에 anti-slop 검사가 있으면 규칙 파일(graphai-repository/anti-slop 의 `rules/rules.yaml`, `rules/vocabulary/ko.yaml`)을 `gh api` 로 읽어 검출 어휘를 대체어로 바꾼다. 실행 파일은 내려받거나 실행하지 않는다.
3. 코드 스팬 밖의 `~` 는 GitHub 에서 취소선이 되므로 범위는 `R-001-R-006` 처럼 하이픈으로 쓴다.
4. 결과 문서의 첫 문장에 PR 작성자(`gh pr view --json author` 의 login)를 `@login` 으로 멘션한다. 후속 리뷰도 같다. 멘션은 기여자가 리뷰를 받았다는 알림의 유일한 경로다.
5. 게시하거나 수정한 뒤 anti-slop 실행이 모두 끝날 때까지 기다리고, bot thread 댓글에서 자기 코멘트 id 의 section 을 확인한다. section 이 없으면 검출 0건이다. 검출이 있으면 같은 코멘트를 수정하고 다시 확인한다.
6. 다른 작성자의 코멘트와 변경 파일에서 나온 검출은 수정하지 않고 보고한다.

## Install and Update

먼저 [osiri](../osiri/SKILL.md), [refactor](../refactor/SKILL.md), [sucks](../sucks/SKILL.md)를 설치한다. `rv`는 검토 과정에서 이 스킬들을 참조한다.

PowerShell (Windows):

```powershell
irm https://raw.githubusercontent.com/zer0ken/skills/main/codex/rv/install.ps1 | iex
```

Bash (macOS / Linux / WSL):

```bash
curl -fsSL https://raw.githubusercontent.com/zer0ken/skills/main/codex/rv/install.sh | bash
```

설치 명령을 다시 실행하면 최신 버전으로 갱신한다.
